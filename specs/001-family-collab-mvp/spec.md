# 功能规格：家庭协作 MVP

**功能分支**: `001-family-collab-mvp`

**创建日期**: 2026-06-01

**状态**: 草案

**输入**: 基于 `RESEARCH.md` — 家庭协作项目，帮助父母了解与管理孩子情况；含登录注册、加入团队、双区任务栏、任务分发（作业/课程/运动）。

## 用户场景与测试 *(mandatory)*

### 用户故事 1 - 注册与登录（优先级：P1）

作为家长或孩子，我希望通过注册与登录使用独立账户，以便只看到属于自己的数据与任务。

**优先级理由**: 账户隔离是团队、任务栏与分发功能的前提，无登录则无法保证数据独立。

**独立测试**: 注册新用户 → 登录 → 在未加入团队时仅能看到空任务栏与个人资料；另一账户无法看到该用户数据。

**验收场景**:

1. **Given** 未注册用户，**When** 使用有效信息完成注册，**Then** 可立即登录并进入个人主页（任务栏可为空）。
2. **Given** 已注册用户，**When** 使用正确凭据登录，**Then** 进入上次会话所属账户视图，且仅展示该用户相关数据。
3. **Given** 已登录用户，**When** 退出登录，**Then** 需重新登录才能再次访问受保护内容。

---

### 用户故事 2 - 加入团队（优先级：P2）

作为团队创建者，我希望邀请他人加入我的家庭团队且需对方同意，以便家庭成员在同一协作空间内工作。

**优先级理由**: 任务分发与审批发生在团队内；无团队则无法验证「a 给 b 分发」场景。

**独立测试**: 用户 A 创建/拥有团队并发出邀请 → 用户 B 在待处理邀请中接受 → A、B 在彼此团队中可见对方成员身份。

**验收场景**:

1. **Given** 已登录用户 A 且无团队，**When** A 创建团队并邀请已注册用户 B，**Then** B 收到待处理邀请且团队对 B 不可见直至接受。
2. **Given** B 有待处理邀请，**When** B 接受邀请，**Then** A 与 B 同属一个团队，成员列表包含双方显示名称。
3. **Given** B 有待处理邀请，**When** B 拒绝邀请，**Then** B 不加入团队，A 收到拒绝结果（或邀请状态为已拒绝）。
4. **Given** 用户已在一个团队中，**When** MVP 范围内，**Then** 系统仅支持单团队归属（见假设）；重复创建第二团队被禁止或引导先离开当前团队。

---

### 用户故事 3 - 个人双区任务栏（优先级：P3）

作为任意已登录成员，我希望在任务栏上方看到未完成事项、下方看到已完成事项，以便一眼区分待办与历史。

**优先级理由**: 任务栏是所有任务类型的统一呈现层；需在无分发任务时也能展示空状态与分区结构。

**独立测试**: 登录用户 → 手动或通过测试数据拥有一条未完成与一条已完成记录 → 验证上下分区位置与条目归属正确。

**验收场景**:

1. **Given** 已登录用户，**When** 打开任务栏，**Then** 页面上方为「未完成」区域，下方为「已完成」区域，且区域标题为中文。
2. **Given** 用户有一条未完成任务，**When** 将其标记完成，**Then** 该条从上方移至下方，完成时间或顺序可辨认。
3. **Given** 用户无任何任务，**When** 打开任务栏，**Then** 两区均显示友好中文空状态提示，非错误页。

---

### 用户故事 4 - 分发课程与运动类任务（优先级：P4）

作为团队中的布置者 A，我向接收者 B 分发「课程」或「运动」任务（含内容与时长），B 无需确认即可在未完成区看到，完成后可直接打勾。

**优先级理由**: 实现两种较简单的任务类型，验证团队内分发与直接完成路径，为作业审批流铺路。

**独立测试**: A、B 同团队 → A 向 B 创建课程任务 → B 任务栏上方出现该任务 → B 打勾 → 任务移至 B 的已完成区。

**验收场景**:

1. **Given** A、B 在同一团队且 A≠B，**When** A 向 B 分发课程类任务并填写内容与时长，**Then** B 的未完成区立即出现该任务，无需 B 点击接受。
2. **Given** B 有未完成的运动类任务，**When** B 点击完成（打勾），**Then** 任务进入 B 的已完成区，A 可查看 B 的完成状态（只读）。
3. **Given** A 尝试向非团队成员 C 分发，**When** 提交，**Then** 系统拒绝并提示中文错误信息。
4. **Given** A 尝试向自己分发，**When** MVP 范围内，**Then** 系统拒绝（布置者与接收者必须为不同成员）。

---

### 用户故事 5 - 分发作业类任务与审批闭环（优先级：P5）

作为布置者 A，我向 B 分发「作业」任务；B 完成后点「审批」，A 的未完成区自动出现「审批 {B 的用户名} 的作业」任务，A 打勾后闭环结束。

**优先级理由**: 作业类型是 RESEARCH 中唯一需要双向审批流的类型，体现家长监督场景。

**独立测试**: A 分发作业 → B 完成并点审批 → A 出现审批任务 → A 打勾 → 双方任务状态符合预期。

**验收场景**:

1. **Given** A 向 B 分发作业并填写内容与时长，**When** 创建成功，**Then** B 的未完成区出现作业任务，类型标识为「作业」。
2. **Given** B 已完成作业执行，**When** B 点击「审批」，**Then** B 侧作业进入已完成（或「待家长审批」子状态，见 FR-020），且 A 的未完成区自动新增一条任务，标题或摘要包含 B 的用户名与「作业」语义。
3. **Given** A 有待审批作业任务，**When** A 打勾完成该审批任务，**Then** 该条进入 A 的已完成区，且与 B 的作业任务形成可追踪的关联（同一业务任务 ID 或等价关联）。
4. **Given** B 已对同一作业点击审批，**When** B 再次点击审批，**Then** 系统不重复为 A 创建审批任务。

---

### 边界情况

- 邀请指向未注册邮箱/账号：提示对方需先注册或邀请无效。
- 网络中断时提交分发：显示失败提示，不部分写入导致 B 看不到任务。
- 团队成员被移除后：其未完成任务如何处理 — MVP 默认保留在本人栏直至完成或手动归档（见假设）。
- 时长字段为空或非法：阻止提交并中文校验提示。
- 并发：两名成员同时向 B 分发多条任务，B 的未完成区按创建时间排序展示全部。
- 用户显示名称重复：审批任务文案 MUST 使用可区分成员标识（用户名或系统 ID 缩写）。

## 需求 *(mandatory)*

### 功能需求

- **FR-001**: 系统 MUST 提供注册与登录，且每个用户只能访问本人账户下的团队、任务与邀请数据。
- **FR-002**: 系统 MUST 使用凭据校验登录；MVP 默认支持「邮箱 + 密码」（见假设）。
- **FR-003**: 用户 MUST 能够创建家庭团队并成为该团队创建者。
- **FR-004**: 团队创建者 MUST 能够向其他已注册用户发出加入邀请。
- **FR-005**: 被邀请者 MUST 在明确接受后方可加入团队；拒绝后不得获得团队数据访问权。
- **FR-006**: 每位用户 MUST 拥有个人任务栏，分为上下两区：上方仅展示未完成项，下方仅展示已完成项。
- **FR-007**: 团队内成员 A MUST 能够向另一成员 B（A≠B）分发任务，且 B 无需确认即可在未完成区看到。
- **FR-008**: 分发任务时 MUST 选择任务类型：作业、课程、运动三者之一。
- **FR-009**: 分发时 MUST 填写任务「内容」与「时长」；两项均为必填。
- **FR-010**: 课程类与运动类任务，接收者 B 完成后 MUST 可通过单次「完成/打勾」操作将任务移入已完成区。
- **FR-011**: 作业类任务，接收者 B 完成后 MUST 通过「审批」操作触发向布置者 A 的审批待办，而非仅本地打勾结束。
- **FR-012**: B 点击「审批」后，A 的未完成区 MUST 自动出现审批类任务，文案 MUST 包含 B 的用户名及作业语义（如「审批 {用户名} 的作业」）。
- **FR-013**: A 对审批任务打勾完成后，该审批任务 MUST 进入 A 的已完成区。
- **FR-014**: 系统 MUST 防止同一作业重复生成多条待审批任务给 A。
- **FR-015**: 布置者 MUST 能够查看所分发任务在接收者侧的完成/审批状态（列表或详情只读）。
- **FR-016**: 所有面向用户的标签、按钮、错误与空状态 MUST 使用简体中文。
- **FR-017**: UI MUST 符合项目宪章：禁止蓝紫渐变主视觉；MVP 建议主色为暖中性色（如 `#C67B5C` 陶土色、`#F5F0EB` 米白背景），不使用 `blue→purple` 类渐变按钮或背景。
- **FR-018**: MVP 中每位用户 MUST 仅属于一个团队；退出/解散团队流程可简化为「暂不支持」，在文档中说明。
- **FR-019**: 「时长」MVP 接受用户输入的正整数分钟数，界面显示为「{n} 分钟」；若用户需自由文本，可在后续版本扩展。
- **FR-020**: B 点击「审批」后，B 侧作业任务 MUST 标记为已完成或「已提交审批」状态，且不可再次提交审批。

### 关键实体

- **用户（User）**: 账户标识、显示名称、登录凭据；与团队、任务、邀请一对多关联。
- **团队（Team）**: 家庭协作单位；包含多名成员；由创建者发起邀请。
- **团队邀请（TeamInvitation）**: 邀请方、被邀请方、状态（待处理/已接受/已拒绝）。
- **任务（Task）**: 类型（作业/课程/运动）、内容、时长（分钟）、布置者、接收者、完成状态、关联审批任务 ID（作业专用）。
- **审批待办（ApprovalTask）**: 由作业审批触发的、仅出现在布置者未完成区的特殊任务，关联原作业任务。

## 成功标准 *(mandatory)*

### 可衡量结果

- **SC-001**: 新用户可在 3 分钟内完成注册、登录并看到个人任务栏空状态。
- **SC-002**: 邀请发出后，被邀请者在 2 分钟内可完成接受并出现在同一团队成员列表。
- **SC-003**: 布置者分发任务后，接收者在刷新或进入任务栏后 5 秒内能看到新未完成项（无需确认操作）。
- **SC-004**: 课程/运动任务从分发到接收者打勾完成，全程不超过 4 次主要用户操作（登录不计）。
- **SC-005**: 作业从 B 点击「审批」到 A 未完成区出现审批任务，延迟在单次页面加载时间内可感知（用户主观「即时」）。
- **SC-006**: 在 5 人以内团队、每人 20 条任务的测试规模下，任务栏分区加载与切换无明显卡顿（用户可连续操作而不放弃）。
- **SC-007**: 90% 的验收场景可在无英文 UI 文案的情况下由中文母语测试者执行通过。

## 宪章合规 *(mandatory)*

- **UI**: 符合原则 I；主色建议暖陶土/米白/深灰文字，主按钮为纯色填充，禁止蓝紫渐变 hero/按钮/背景。
- **语言**: 本规格及全部 UI 为简体中文；「MVP」「ID」等技术缩写仅用于规格正文，不出现在用户界面。
- **交付**: 实现按用户故事分次提交；本功能全部故事验收后更新根目录 `README.md` 并推送 `origin`。

## 假设

- 目标用户为中文家庭，主要角色为家长（布置者）与孩子（接收者），但 MVP 不限制角色字段，任意团队成员均可作为 A 或 B。
- 认证方式为邮箱 + 密码；无第三方 OAuth、无短信验证码（后续版本可加）。
- 每用户仅一个团队，简化邀请与权限模型。
- 邀请通过系统内用户标识（邮箱或用户名）发送，不支持仅外链匿名加入。
- 「时长」为整数分钟，最小 1、最大 480（8 小时），超出范围校验失败。
- 无推送通知 MVP；用户通过刷新或重新进入任务栏感知新任务。
- 无子任务、无截止日期、无附件；任务「内容」为单行或多行纯文本。
- 团队解散、成员踢出、任务删除为 MVP 外或最低优先级，除非阻碍测试。

## 范围外（MVP 不包含）

- 多团队、子团队、班级批量导入
- 统计报表、成长档案、日历视图
- 消息推送、微信登录
- 任务评论、附件、重复周期任务
- 移动端原生 App（优先响应式 Web）
